#+title: Project Overview
This project provides rule-based auto-approval of tool calls for gptel's agentic LLM usage. Rules match tool calls by name and argument regexps, then auto-allow, auto-deny, or force-confirm.

* Basic Project Structure
- =gptel-permit.el= :: The rule engine core. Defines permission rules, condition predicates, the pre-tool-call security hook, the action registry (`gptel-permit-action-handlers`), the three engine hooks, tool-call-id minting, and the global custom options. Contains no module-specific code: it runs and stays meaningful with no optional module loaded.
- =gptel-permit-judge.el= :: The optional `llm-judge` module: the `gptel-permit-judge-safe-p` condition callable, which asks a small local model whether an argument value is obviously safe. Fail-closed on every error path (never blocks; a failed judgement just makes the rule not match) and retains the verdict's rationale for analytics. Owns its per-call state and clears it via `gptel-permit-before-rule-match-functions`, self-registered at load.
- =gptel-permit-sandbox.el= :: The `sandbox` rule action: the backend registry (`gptel-permit-sandbox-backends`; CLOS classes under the `gptel-permit-sandbox-backend-base` base class implementing two generics), the tool-adapter registry (`gptel-permit-sandbox-adapters`), platform-table `auto` backend resolution, protected-path binding from the core option, the pre-tool args-rewrite verdict, the sticky boundary-failure latch (`gptel-permit-sandbox-reset`), and the `C-c C-s` sandboxed-accept command. Self-registers its action handler in `gptel-permit-action-handlers`, its post-tool tracker on `gptel-post-tool-call-functions`, and `C-c C-s` in `gptel-tool-call-actions-map` at load; a sandbox rule with the module absent fails closed via the engine's unregistered-action path. Holds no backend-specific wrapper construction.
- =gptel-permit-sandbox-bwrap.el= :: The bubblewrap backend: the `gptel-permit-sandbox-backend-bwrap` class with its `available-p`/`wrap` methods, plus the bwrap-only options (`gptel-permit-sandbox-command`, =-network=, =-env-keep=, =-extra-args=). Appends its registry entry at load and is required lazily by the sandbox core on first use; doubles as the copy-paste template for third-party backends.
- =gptel-permit-sandbox-srt.el= :: The Anthropic sandbox-runtime backend: the `gptel-permit-sandbox-backend-srt` class with its methods, `gptel-permit-sandbox-allowed-domains`, and the settings-JSON generation. Same lazy-load and self-registration contract as the bwrap module.
- =gptel-permit-analytics.el= :: The optional `analytics` module: an append-only local JSONL decision log, audit sampling that up-ranks automation-allow verdicts to manual confirms, decision-capture advice on gptel's three interactive tool-call commands, and pure statistics/report functions. Inert until `gptel-permit-register-analytics-hooks` is called. Captures engine events through `gptel-permit-events-functions` and samples through `gptel-permit-veto-functions`; the core calls no analytics function by name. Tool-call ids arrive from the core as `TIMESTAMP.PID.SERIAL` strings.
- =tests/= :: ERT test suites covering argument normalization, rule matching, engine hooks, validation, the security hook, the modules (including the sandbox backend registry, adapter dispatch, and latch semantics), and analytics (including the cross-module judge-state-leak acceptance test).
- =README.org= :: User-facing documentation (installation, configuration, usage, extension points).
- =Makefile= :: Batch test runner plus the staged multi-package build check (=make package-build=).

* Packaging: one repository, four packages

The code is shipped as four packages from this single repository, each
selecting its files via its MELPA recipe's =:files= directive (the
=gptel-permit-judge=.el / =gptel-permit-sandbox.el= / =gptel-permit-analytics.el=
pattern from =embark=/=embark-consult=):

| Package                 | Files (:files)                                                                    |
|-------------------------+------------------------------------------------------------------------------------|
| =gptel-permit=          | =gptel-permit.el=                                                                  |
| =gptel-permit-judge=    | =gptel-permit-judge.el=                                                            |
| =gptel-permit-sandbox=  | =gptel-permit-sandbox.el=, =gptel-permit-sandbox-bwrap.el=, =gptel-permit-sandbox-srt.el= |
| =gptel-permit-analytics= | =gptel-permit-analytics.el=                                                        |

Hard =require= edges go only to the core; soft cross-module references
(analytics→judge buffer-locals via feature guards, analytics→sandbox
`--rewritten-args` dynamic read, judge→sandbox through the action registry)
stay soft and are NOT listed in any Package-Requires. All four packages
version in lockstep (=Version: 0.1.0=; modules pin =(gptel-permit "0.1.0")=).

The build-enforcement invariant lives in =make package-build=: it stages
each package's files as package.el would and byte-compiles every module
against ONLY the staged core — so an accidental sibling require fails the
build, not a user's fresh install. Adding to the core's module-facing
surface requires editing the "Module interface" section in =gptel-permit.el=
and the =rule-engine-api= spec.

* Development Approach

Agents SHALL keep changes small and testable:
1. *Understand the hook protocol*: =gptel-permit--apply-rules= receives a plist of ~(:name :args :buffer :backend :model)~, where =:buffer= is the session buffer's name string (pass it through =get-buffer=, never =with-current-buffer= directly) and =:backend= the =gptel-backend= struct (pass it to =gptel-backend-name=). It returns ~(:confirm nil)~ (auto-accept), ~(:confirm t)~ (force prompt), ~(:block "<reason>")~ (reject), ~(:confirm nil :args (:command …))~ (args rewrite; the sandbox verdict), or ~nil~ (defer).
2. *Match rules predictably*: Session-local rules (=gptel-permit-rules=) always take precedence over global rules (=gptel-permit-global-rules=). All conditions in a rule must match for the action to fire.
3. *Never miss a hard block*: Path traversal checks in =Write= and =Mkdir= fire before any rule matching and cannot be overridden by rules.
4. *Log when debugging*: Rule matching is silent by default. Set =gptel-permit-log-enabled= to =t= to write diagnostics into =*gptel-permit-log*=.

Keep elisp functions under 60 lines. The package is a core library plus
three optional modules and two lazily loaded backend libraries (bwrap,
srt); new functionality that is not core rule evaluation belongs in a
module or registers through the core's extension points, never as core
knowledge of a module's symbols.

* Essential Development Commands
- Run test suite: =make test=
- Run a single test interactively: ~M-x ert RET gptel-permit-match-rule RET~
- Byte-compile to check for warnings: ~M-x emacs-lisp-byte-compile RET gptel-permit.el RET~

* Integration Surface
Every change must respect these integration points:
- ~gptel-pre-tool-call-functions~ (hook) :: =gptel-permit= registers =gptel-permit--validate-args= and =gptel-permit--apply-rules= here when the mode is enabled. The hook is called by gptel's internal =gptel--handle-pre-tool=. Do not remove or rename this hook; if the signature changes, update tests.
- ~gptel-post-tool-call-functions~ (hook) :: gptel's post-execution hook. Touched by the sandbox module at load (boundary-failure tracking; inert unless a command was wrapped). The minor mode no longer registers anything here.
- ~gptel-permit-action-handlers~ (core alist) :: The action registry: action symbol → handler called as ~(ID TOOL-CALL)~ returning a verdict plist or nil. The core resolves matched actions only through it; a matched action with no handler fails closed (~(:confirm t)~). Modules register their actions at load, idempotently.
- ~gptel-permit-before-rule-match-functions~ (core abnormal hook) :: ~(ID TOOL-CALL)~, run once per call before matching; per-call state lifecycle. Errors fail closed.
- ~gptel-permit-events-functions~ (core abnormal hook) :: ~(ID TOOL-CALL TYPE PAYLOAD)~, the observer tap for the decision chain (:tool-call, :rule-match, :verdict, :confirm; the type set is open). Observers are per-function error-isolated and can never alter a verdict.
- ~gptel-permit-veto-functions~ (core abnormal hook) :: ~(ID TOOL-CALL VERDICT)~ via =run-hook-with-args-until-success=, only when a rule matched. A non-nil return makes the engine upgrade the verdict to ~(:confirm t)~ preserving =:args=. Errors fail closed.
- ~gptel-tool-call-actions-map~ (keymap) :: =C-c C-b= is bound to =gptel-permit-add-rule=, and the sandbox module binds =C-c C-s= to =gptel-permit-accept-tool-calls-sandboxed= at load. This keymap is applied to tool-call overlays by gptel. Do not bind other keys here without good reason.
- ~gptel--accept-tool-calls~ (private function) :: Called by =gptel-permit-add-rule= to execute approved tool calls, and by the sandbox's =C-c C-s= command with rewritten args (analytics matches those rewritten accepts back to their original args through `gptel-permit-sandbox--rewritten-args`). This is gptel internal API — fragile but necessary. If gptel upstream changes it, =gptel-permit= must follow.
- ~gptel-permit-sandbox-backend-base~ / ~gptel-permit-sandbox-backends~ / ~gptel-permit-sandbox-adapters~ (sandbox extension points) :: A backend is a subclass of =gptel-permit-sandbox-backend-base= implementing =gptel-permit-sandbox-available-p= and =gptel-permit-sandbox-wrap=, registered as symbol → class symbol in =gptel-permit-sandbox-backends=; tool adapters are function-valued (="TOOL-NAME" → (:wrap-args FN)=) in =gptel-permit-sandbox-adapters=. The base class MUST NOT be named =gptel-permit-sandbox-backend=: EIEIO binds a class name as a variable, which would clobber the option of the same name — the regression test is =gptel-permit-sandbox-default-option-is-auto=. Both registries are user-visible configuration; keep their entries inert printable data (symbols), not objects.
